title: Store canonical items in per-type folders and generate the ledgers
status: accepted
context: >-
  VEF currently embeds every structured item in a monolithic root ledger, although an older agent profile described
  per-item fragments. Large ledgers increase merge contention and make deterministic create/update operations rewrite
  shared files. The intended human-readable ledgers are still valuable as complete GitHub- and agent-friendly views.
decision: >-
  Make one Markdown file per structured item canonical, organized by record type under the documentation namespace
  (docs/roadmap/, docs/tasks/, docs/decisions/, and docs/vision/ where themes are structured). Keep ROADMAP.md,
  TASKS.md, DECISIONS.md, and the structured theme view in VISION.md as deterministic, committed projections generated
  from those item files. Keep ARCHITECTURE.md, log.md, and index.md as canonical singleton documents. Preserve stable
  public ledger anchors such as /TASKS.md#TASK-011; direct item paths provide record-level identity. Validation must
  reject stale or non-reproducible projections.
rationale: >-
  Per-item sources isolate Git diffs and concurrent agent work, provide natural record identities, and give the
  transaction core a precise write target. Generated ledgers preserve excellent sequential reading and stable public
  links without maintaining a second hand-edited source of truth. Placing the collections under docs/ avoids collisions
  with application-owned directories and gives review tooling one coherent content root. The projector and validation
  gate make the duplication explicit and mechanically controlled.
consequences: >-
  Positive — smaller diffs, lower merge contention, deterministic creation, clearer ownership, reusable projections, and
  an explicit consumer upgrade path. Negative — VEF must maintain the canonical loader, stable ordering, projection
  templates, migration compatibility, drift detection, and the rule that generated ledgers are not edited directly.
  Legacy repositories must commit a coordinated one-time migration before strict validation passes on the new contract.

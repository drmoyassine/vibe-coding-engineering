## DEC-002 — Adopt the OKF v0.2 pattern (index.md, log.md, actor convention, trust signals) with product-doc extensions

---
id: DEC-002
title: Adopt the OKF v0.2 pattern (index.md, log.md, actor convention, trust signals) with product-doc extensions
status: accepted
context: >-
  The framework's markdown + YAML-frontmatter design independently converged on the same pattern as Google's Open
  Knowledge Format (OKF) and the LLM-Wiki/OpenKB ecosystem. Aligning explicitly lets us (a) reuse OKF's
  reserved-filename and trust-signal conventions, (b) position the framework as an OKF extension for product
  documentation, and (c) be referenceable in media/literature against OKF and OpenKB.
decision: >-
  Adopt the OKF v0.2 conventions that fit product docs: `index.md` (navigation hub + `okf_version`), `log.md`
  (chronological changelog replacing ad-hoc session memory), the actor convention (`human:<id>` / `<producer>/<version>`
  / `process:<id>`), and the trust-signal fields (`generated`, `verified`). Add the `resource` and `tags` optional
  fields. Keep our existing extensions: structured `id + name + url` cross-linking, bidirectional relationships, the
  four management skills, and multi-repo support.
rationale: >-
  OKF is a vendor-neutral, agent- and human-friendly open spec. Conforming to it costs nothing (we already use markdown
  + YAML frontmatter) and gains interoperability: any OKF consumer (visualizer, agent, search tool) can read our docs.
  Our extensions (relationship types, skills, multi-repo) are the differentiated value — the framework is 'OKF for
  product docs.' Adopting `log.md` also resolves the memory-drift problem: session learnings become a version-controlled
  changelog instead of gitignored, per-repo auto-memory.
consequences: >-
  Positive — OKF conformance + literature-ready positioning; drift eliminated (log.md replaces misplaced memory
  content); trust signals align with the agent-hallucination guard work (agent-written content can be marked
  provisional/unverified). Negative — schema grows (more optional fields to document); `log.md` must be maintained (or
  it rots like any changelog). Attested-Computation fields and `sources` provenance are NOT adopted (out of scope for
  product-docs).

**What we adopt from OKF v0.2:**

| OKF concept | Our implementation |
|-------------|--------------------|
| `index.md` (reserved filename) | Repo-root navigation hub with `okf_version` frontmatter |
| `log.md` (reserved filename) | Chronological changelog; replaces session-scoped auto-memory for durable learnings |
| Actor convention (§7) | `generated.by` / `verified.by` use `human:<id>`, `<producer>/<version>`, `process:<id>` |
| Trust signals (`generated`, `verified`) | Optional fields on all items; advisory tiers (Unverified / Machine-confirmed / Human-reviewed) |
| `resource` field | Canonical URI to the underlying artifact (migration, PR, code) |
| `tags` field | Free-form cross-cutting labels |
| Format-not-platform | Git-native, no proprietary lock-in (already true) |

**What we do NOT adopt:** Attested Computation (`runtime`/`executor`/`attester`) — data-pipeline scope, not product docs. `sources` provenance family — deferred until decisions commonly cite external standards.

**Our extensions beyond OKF:** structured `id + name + url` relationship types (`depends_on`, `related_tasks`, `related_decisions`, `roadmap_item`), bidirectional cross-linking, four management skills (`/tasks` `/roadmap` `/bugs` `/decisions`) + `/apply` migration, multi-repo canonical/consumer split.

title: Make the Integrity Core authoritative and keep agent adapters portable
status: accepted
context: >-
  VEF's product promise is a trustworthy, typed project model, but the current implementation contains several competing
  schema descriptions, partial backlink checks, permissive validation paths, and a Claude-specific workflow layer. Agent

decision: >-
  Adopt a portable VEF Core composed of one machine-readable schema, a typed relationship model, deterministic

## DEC-004 — Store canonical items in per-type folders and generate the ledgers

---
id: DEC-004
title: Store canonical items in per-type folders and generate the ledgers
status: accepted
context: >-
  VEF currently embeds every structured item in a monolithic root ledger, although an older agent profile described
  per-item fragments. Large ledgers increase merge contention and make deterministic create/update operations rewrite
  shared files. The intended human-readable ledgers are still valuable as complete GitHub- and agent-friendly views.
decision: >-
  Make one Markdown file per structured item canonical, organized by record type under the documentation namespace
  (docs/roadmap/, docs/tasks/, docs/decisions/, and docs/vision/ where themes are structured). Keep ROADMAP.md,
  TASKS.md, DECISIONS.md, and the structured theme view in VISION.md as deterministic, committed projections generated
  from those item files. Keep ARCHITECTURE.md, log.md, and index.md as canonical singleton documents. Preserve stable
  public ledger anchors such as /TASKS.md#TASK-011; direct item paths provide record-level identity. Validation must
  reject stale or non-reproducible projections.
rationale: >-
  Per-item sources isolate Git diffs and concurrent agent work, provide natural record identities, and give the
  transaction core a precise write target. Generated ledgers preserve excellent sequential reading and stable public
  links without maintaining a second hand-edited source of truth. Placing the collections under docs/ avoids collisions
  with application-owned directories and gives review tooling one coherent content root. The projector and validation

## DEC-006 — Keep review interfaces disposable and canonical records authoritative

---
id: DEC-006
title: Keep review interfaces disposable and canonical records authoritative
status: accepted
context: >-
  VEF audits, migrations, and reconciliations can produce dense but valid Markdown changes that still require human
  judgment. Git diffs and linear ledgers are durable but not always an effective review experience. Earlier roadmap
  items proposed a rendered website and an Obsidian plugin, but they did not define a shared acceptance and comment
  boundary.
decision: >-
  Add a tool-neutral human review layer as a disposable projection of canonical VEF state. A review bundle may contain
  rendered documents, normalized records, typed graph context, validation results, provenance, candidate diffs, review
  queues, and comments anchored to stable targets. Comments are stored in an exportable review packet and remain
  untrusted review evidence until explicitly reconciled into canonical Markdown and accepted by strict validation. The
  initial review UI must not own a project database or silently mutate canonical records. Obsidian, wiki, static-site,
  and future hosted adapters consume this shared contract rather than defining competing formats.
rationale: >-
  Humans need a lower-friction way to understand and annotate agent-produced project state, while VEF's portability
  depends on Markdown and Git remaining authoritative. A neutral ephemeral bundle provides useful interaction
  immediately, avoids requiring a hosted product, and prevents each UI adapter from inventing its own parsing, comments,
  and write-back semantics.
consequences: >-
  Positive — faster human acceptance, visible provenance and uncertainty, portable review handoffs, reusable UI
  adapters, and no new canonical store. Negative — VEF must version stable review targets and comment packets, secure
  rendering of untrusted content, distinguish review from acceptance clearly, and eventually connect approved feedback
  to the validated mutation layer. Exported review packets may contain sensitive project context and require explicit
  handling guidance.
